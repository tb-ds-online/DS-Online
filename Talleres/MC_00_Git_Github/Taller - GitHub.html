Lo primero

Git no es GitHub

Git

Programa que guarda la historia de tu proyecto. Funciona en tu ordenador, sin internet y sin cuenta.

Es la herramienta.

GitHub

Plataforma web que aloja repositorios Git y añade colaboración: pull requests, issues, automatización.

Es un servicio, y no el único.

Para quedarseSi GitHub desaparece mañana, tu Git sigue funcionando. Cada clon tiene la historia completa.

Cómo usarlo · automatizar

Actions: que las pruebas se ejecuten solas

Un archivo YAML en .github/workflows/ dice qué ejecutar y cuándo. Este lanza las pruebas en cada push y en cada pull request.

  • Gratis en repositorios públicos.
  • En privados, el plan Free incluye 2.000 minutos al mes.
  • Si fallan las pruebas, lo ves en la pull request antes de fusionar.
Por qué importa en dataSirve para probar pipelines y regenerar informes sin que nadie se acuerde de hacerlo.
name: Pruebas
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
      - run: pip install -r requirements.txt
      - run: pytest

Tu perfil también es tu CV

  • Crea un repo con tu mismo nombre de usuario: su README.md aparece en tu perfil.
  • Fija tus mejores proyectos, no todos.
  • Cada proyecto, con un README que explique problema, datos y resultado.
  • Nombres claros: prediccion-churn, no prueba_final2.

Terminal · convenciones de commits

  
Un commit se escribe para quien lo lea dentro de seis meses

  

    


tipo(ámbito opcional): descripción

cuerpo opcional: por qué se hace el cambio

      

        
TipoCuándo

        
featFuncionalidad nueva

        
fixCorrección de un bug

        
docsSolo documentación

        
refactorReorganiza sin cambiar el comportamiento

        
testAñade o corrige pruebas

        
choreMantenimiento: dependencias, configuración

      

    

    

      
Las reglas

      
    
        
  • Un commit, un cambio lógico.
    • 
        
  • Asunto de unos 50 caracteres.
    • 
        
  • En imperativo o presente: añade, no añadido.
    • 
        
  • Sin punto final.
    • 
        
  • El equipo acuerda un idioma y lo mantiene.
    • 
      

      
      
      

    

  

  
feat y fix son los tipos que define Conventional Commits; los demás son los habituales. Pueden cambiar según el equipo.






  
Terminal · convenciones de commits

  
El mismo trabajo, dos historias

  

    
Así no


a91f2c3 cambios
7be01d4 arreglos varios
c33a9e0 ahora sí
08d1f77 final_v2_bueno

      
Nadie sabe qué cambió ni a qué commit volver.

    
Así sí


a91f2c3 docs: añade instrucciones al README
7be01d4 fix: corrige fechas nulas en ventas
c33a9e0 test: añade pruebas de la limpieza
08d1f77 feat: elimina duplicados de ventas

      
La historia se lee sola y un git revert tiene un objetivo claro.

  

  
Cuando no quepa en una líneaUsa git commit sin -m para abrir el editor. Deja una línea en blanco tras el asunto y explica el porqué.






  
Terminal · ramas

  
Una rama por cambio, y vuelta a main

  


$ git switch -c filtro-fechas
Switched to a new branch 'filtro-fechas'
$ git add limpieza.py
$ git commit -m "feat: filtra ventas desde 2025"
[filtro-fechas b37e6a8] feat: filtra ventas desde 2025
 1 file changed, 1 insertion(+)
$ git switch main
Your branch is up to date with 'origin/main'.
Switched to branch 'main'
$ git merge filtro-fechas
Updating a09c967..b37e6a8
Fast-forward
 limpieza.py | 1 +
 1 file changed, 1 insertion(+)
$ git log --oneline --graph
* b37e6a8 feat: filtra ventas desde 2025
* a09c967 feat: elimina duplicados de ventas
* aedfae2 chore: crea estructura del proyecto
$ git branch -d filtro-fechas
Deleted branch filtro-fechas (was b37e6a8).

    

      
    
        
  • switch -c crea la rama y se mueve a ella.
    • 
        
  • El merge se hace desde la rama que recibe los cambios.
    • 
        
  • Fast-forward: main no había cambiado, así que Git solo avanza el puntero.
    • 
        
  • Una rama fusionada se puede borrar: los commits se quedan.
    • 
      

      
En equipoEl merge suele hacerse en GitHub con una pull request. En local, primero subes la rama con git push -u origin NOMBRE.

    

  






  
Terminal · ramas en una empresa

  
Gitflow: una rama para cada momento de la entrega

  

  

    
main
Lo que está en producción. Cada entrega lleva un tag de versión.

    
develop
Donde se integra el trabajo de la siguiente versión.

    
feature/*
Sale de develop y vuelve a develop.

    
release/*
Prepara una versión. Va a main y a develop.

    
hotfix/*
Arregla producción. Sale de main y va a main y develop.

    
¿Cuándo?
Software con versiones programadas. Hoy se considera un flujo clásico: muchos equipos usan otros más simples.

  






  
Terminal · en el curso

  
En el curso: main y ramas de trabajo

  

  

    

      
    
        
  • Sin develop, sin tags y sin versiones.
    • 
        
  • Una rama por tarea: feature/limpieza, fix/fechas.
    • 
        
  • Se integra con una pull request revisada por otra persona.
    • 
        
  • Tras el merge, la rama se borra.
    • 
      

    


$ git switch main
$ git pull
$ git switch -c feature/limpieza
$ git add limpieza.py
$ git commit -m "feat: elimina duplicados"
$ git push -u origin feature/limpieza
# Pull request y merge en GitHub
$ git switch main
$ git pull
$ git branch -d feature/limpieza

  






  
Terminal · conflictos

  
Un conflicto no es un error: es una pregunta

  

    


$ git merge cambia-fecha
Auto-merging limpieza.py
CONFLICT (content): Merge conflict in limpieza.py
Automatic merge failed; fix conflicts and then commit the result.

      
Dos ramas tocaron la misma línea. Git no decide por ti y marca el archivo:


import pandas as pd
df = pd.read_csv("ventas.csv").drop_duplicates()
<<<<<<< HEAD
df = df[df["fecha"] >= "2025-06-01"]
=======
df = df[df["fecha"] >= "2024-01-01"]
>>>>>>> cambia-fecha

    

    

      
Cómo resolverlo

      
    
        
  1. Abre el archivo y decide qué versión se queda. Puede ser una tercera.
    2. 
        
  2. Borra las marcas <<<<<<<, ======= y >>>>>>>.
    3. 
        
  3. Guarda y ejecuta el código.
    4. 
        
  4. Haz git add y git commit.
    5. 
      


$ git add limpieza.py
$ git commit -m "fix: resuelve conflicto de fechas"
[main d782e8c] fix: resuelve conflicto de fechas

      
¿Te has perdido?git merge --abort te devuelve a donde estabas.

    

  






  
Terminal · deshacer

  
¿Te has equivocado? Depende de dónde esté el error

  

    
SituaciónComandoEfecto

    
He editado un archivo y quiero volver atrásgit restore archivoPierdes esos cambios

    
Hice add de algo que no debíagit restore --staged archivoSale de staging, el cambio sigue

    
Me he equivocado en el último commit, sin pushgit commit --amendReescribe ese commit

    
Quiero deshacer un commit ya subidogit revert HASHCrea un commit que lo anula

    
Quiero quitar el último commit local y conservar los cambiosgit reset --soft HEAD~1El commit desaparece, los cambios quedan en staging

  

  

    
Ya subido a una rama compartidaUsa revert: no reescribe la historia de tus compañeros.

    
Con cuidadogit reset --hard y git push --force pueden hacer perder trabajo. Antes de usarlos, entiende qué borran.

Ejercicio · paso 2 · cada persona

  
Tu ficha, del issue al merge

  

    
    
      
  1. Abre un issue: Añadir ficha de Ana. Fíjate en su número.
    2. 
      
  2. Crea tu rama y añade equipo/ana.md con tu nombre y qué esperas del bootcamp.
    3. 
      
  3. Haz commit y push.
    4. 
      
  4. Abre una pull request hacia main. Escribe Closes #1 con el número de tu issue.
    5. 
      
  5. Otra persona revisa, comenta y aprueba.
    6. 
      
  6. Haz el merge y borra la rama en GitHub.
    7. 
      
  7. Actualiza tu main.
    8.

$ git pull
$ git switch -c feature/ficha-ana
$ git add equipo/ana.md
$ git commit -m "feat: añade ficha de Ana"
$ git push -u origin feature/ficha-ana
# Pull request, revisión y merge en GitHub
$ git switch main
$ git pull
$ git branch -d feature/ficha-ana

  






  
Ejercicio · paso 3 · dos personas

  
Ahora, un conflicto a propósito

  

    
    
      
  1. Cada persona crea su rama, como fix/lema-ana y fix/lema-luis.
    2. 
      
  2. Las dos cambian la línea Lema: por un lema distinto, hacen commit y push.
    3. 
      
  3. Abren una pull request cada una. Se fusiona solo la primera.
    4. 
      
  4. La segunda verá que GitHub avisa de un conflicto. Lo resuelve en local:
    5. 
    

    


$ git switch main
$ git pull
$ git switch fix/lema-luis
$ git merge main
# Edita README.md y borra las marcas
$ git add README.md
$ git commit -m "fix: resuelve conflicto del lema"
$ git push

      
DespuésLa pull request se actualiza sola. Otra persona la revisa y se fusiona.

    

  






  
Ejercicio · para terminar

  
Comprobad que el repo cuenta la historia

  

    
    
      
  • Hay una ficha por persona en equipo/.
    • 
      
  • Cada issue de ficha está cerrado.
    • 
      
  • Todas las pull requests tienen una revisión de otra persona.
    • 
      
  • Los commits siguen la convención.
    • 
      
  • El lema final no tiene marcas de conflicto.
    • 
      
  • No quedan ramas de trabajo abiertas.
