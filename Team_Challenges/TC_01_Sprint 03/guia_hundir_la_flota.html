Fase 1 de 4

Setup inicial

Repositorio · Protección de main · Roles · Issues

¿Por qué empezar por aquí?

Todo lo que construyáis se apoya en esta base. Un repositorio mal configurado acaba en conflictos, trabajo perdido y commits directos sobre main que cuesta mucho deshacer. Dedicadle 20 minutos al principio y os ahorraréis horas después.

1

Crear el repositorio en GitHub

Lo hace una persona del equipo (el Scrum Master). El resto espera hasta el paso 4.

  1. En GitHub, botón verde New repository.
  2. Nombre: hundir-la-flota.
  3. Visibility: Public, para que los profes podamos verlo.
  4. Marcad Add a README file.
  5. En Add .gitignore, elegid la plantilla Python.
  6. Sin licencia.

Una vez creado, copiad la URL del repo (botón verde Code → HTTPS).

2

Añadir colaboradores

Todos tienen que tener acceso antes de clonar.

  1. Settings → Collaborators → Add people.
  2. Buscad a cada compañero por su usuario de GitHub.
  3. Cada uno acepta la invitación que le llega por email.
  4. Comprobad que todos aparecen en la lista de colaboradores. En un repo personal, ser colaborador ya da permiso para hacer push.
3

Proteger la rama main y configurar los merges

Esto es lo que os hace trabajar como un equipo de verdad. Sin protección, cualquiera puede subir código roto directamente a main.

Settings → Rules → Rulesets → New ruleset → New branch ruleset:

  1. Ruleset name: proteger-main.
  2. Enforcement status: Active.
  3. Target branches: Add target → Include default branch.
  4. Activad:
    • Require a pull request before merging, con Required approvals: 1 (otra persona del grupo tiene que aprobar).
    • Dismiss stale pull request approvals when new commits are pushed: si se suben commits nuevos, hay que volver a aprobar.
    • Block force pushes.

Después, en Settings → General → Pull Requests:

  • Dejad marcado solo Allow merge commits y desmarcad squash y rebase. Así nadie elige otra opción sin querer.
  • Marcad Automatically delete head branches: la rama se borra de GitHub al mergear el PR.
Resultado esperado: si alguien hace git push origin main, GitHub lo rechaza con un error. Es justo lo que queremos.

Fase 2 de 4

Desarrollo

Una rama por issue · Conventional Commits · Docstrings · Ciclo diario

El orden de desarrollo importa

variables.py es la base: no se puede programar la clase sin las constantes, ni las funciones sin la clase. Este es el orden:

1variables.pySin dependencias. Se empieza aquí y se mergea cuanto antes para que los demás lo tengan.
2clases.pyImporta variables.py. Mientras no esté mergeado, se puede avanzar con constantes provisionales.
3funciones.pyPuede ir en paralelo con el final de clases.py. Importa clases y variables.
4main.pyCuando los tres anteriores funcionan. Junta todo.
7

Una rama por issue

Cada tarea se hace en su propia rama, que sale de un main actualizado y muere al mergear su PR.

# Partir siempre de main actualizado
git checkout main
git pull origin main

# Crear la rama del issue y publicarla en GitHub
git checkout -b feature/2-clase-tablero
git push -u origin feature/2-clase-tablero

Nombre de rama: tipo/numero-de-issue-descripcion. Por ejemplo feature/1-variables, feature/3-funciones, fix/7-disparo-repetido o docs/5-readme.

Regla de oro: no sigáis trabajando en una rama cuyo PR ya está mergeado. Para la siguiente tarea, volved a main, haced pull y cread una rama nueva. Reutilizar ramas viejas es la causa número uno de conflictos raros.
8

Conventional Commits: el formato que vamos a usar

Un historial de commits legible es lo que distingue un proyecto profesional de uno caótico.

tipo: descripción corta en imperativo

# Tipos
feat:      nueva funcionalidad
fix:       corrección de un bug
refactor:  reorganizar código sin cambiar lo que hace
docs:      documentación (docstrings, README)
test:      pruebas
chore:     configuración (.gitignore, requirements.txt…)

✗ Así no

  • arreglado
  • cambios
  • wip
  • funciona
  • final final v2

✓ Así sí

  • feat: añadir método recibir_disparo
  • fix: evitar barcos fuera del tablero
  • docs: añadir docstring a colocar_barcos
  • refactor: extraer validación de coordenadas
  • chore: añadir numpy a requirements.txt

Docstrings: documentar mientras se programa

No lo dejéis para el final. Cada clase, método y función lleva su docstring desde que se escribe. Usamos el formato Google Style:

class Tablero:
    """
    Tablero de juego de un jugador.

    Attributes:
        id_jugador (str): Identificador del jugador.
        tamano (int): Lado del tablero (tamano x tamano).
        tablero (np.ndarray): Barcos del jugador y disparos recibidos.
        disparos (np.ndarray): Solo los disparos recibidos, sin barcos.
    """

    def recibir_disparo(self, fila: int, columna: int) -> str:
        """
        Procesa un disparo en la casilla (fila, columna).

        Args:
            fila (int): Fila del disparo, de 0 a 9.
            columna (int): Columna del disparo, de 0 a 9.

        Returns:
            str: "tocado", "agua" o "repetido".
        """
10

El ciclo de cada día

Cada vez que os pongáis a trabajar, seguid este ciclo sin saltaros pasos.

  1. Traer lo último de main, por si un compañero ha mergeado algo:
git checkout main
git pull origin main
  1. Volver a vuestra rama y meterle esos cambios:
git checkout feature/2-clase-tablero
git merge main --no-edit
# Si hay conflictos, mirad el paso 14
  1. Programar, añadir y hacer commit, en commits pequeños:
git status
git add clases.py
git commit -m "feat: implementar colocar_barcos con orientación N/S/E/O"
  1. Subir los cambios:
git push origin feature/2-clase-tablero
¿Por qué --no-edit? Un merge crea un commit con un mensaje automático. Sin esa opción, Git abre un editor en el terminal para que lo confirméis y muchos os quedaréis atrapados en Vim. Con --no-edit acepta el mensaje por defecto.

Integración

El ciclo completo de un Pull Request

Es el flujo que vais a encontrar en cualquier empresa: todo lo que entra en main pasa por un PR revisado por otra persona. Sin excepciones.

11

Abrir el Pull Request

Cuando vuestra tarea esté lista para revisar: no tiene que ser perfecta, pero sí funcionar.

  1. En GitHub: pestaña Pull requests → New pull request.
  2. base: main ← compare: feature/2-clase-tablero.
  3. Título: mismo formato que los commits.
  4. Descripción: usad esta plantilla.
Plantilla
## ¿Qué hace este PR?
Implementa la clase Tablero con __init__, colocar_barcos(), recibir_disparo() y mostrar().

## Cambios
- clases.py: clase Tablero completa
- variables.py: añadidos los símbolos TOCADO y AGUA_DISPARADA

## Cómo probarlo
python -c "from clases import Tablero; t = Tablero('jugador'); t.colocar_barcos(); t.mostrar()"

## Checklist
- [x] El código funciona sin errores
- [x] Docstrings en todos los métodos
- [x] Sin print() de depuración
- [x] Sin valores escritos a mano: todo en variables.py
- [x] He hecho git merge main antes de abrir el PR

Closes #2
  1. Assignees: el autor.
  2. Reviewers: un compañero distinto del autor.
  3. El Closes #2 enlaza el PR con su issue y lo cierra al mergear.
12

Code review: cómo revisar y cómo recibir la revisión

Quien revisa es el guardián de la calidad. Su trabajo no es aprobarlo todo, sino encontrar problemas antes de que lleguen a main.

Qué mirar al revisar

  • ¿El código hace lo que dice el PR? Bajad la rama y probadlo.
  • ¿Los nombres se entienden?
  • ¿Hay números escritos a mano que deberían estar en variables.py?
  • ¿Quedan print() de depuración?
  • ¿Hay docstrings?
  • ¿Qué pasa en los casos límite: coordenada fuera de rango, disparo repetido, barco en el borde?

Cómo responder a una revisión

  • Leed cada comentario con calma y sin poneros a la defensiva.
  • Responded a todos: o hacéis el cambio o explicáis por qué no.
  • Subid los arreglos a la misma rama y pedid otra revisión.
  • Como mínimo, una ronda de revisión antes de mergear.

Para comentar una línea: pestaña Files changed y clic en el + que aparece junto al número de línea. Comentarios concretos:

Comentario vagoComentario útil
«Esto no me gusta»«Este 10 debería ser TAMANO_TABLERO de variables.py»
«No funciona»«Con fila 10 salta un IndexError: falta validar el rango»
«Cámbialo»«¿Y si sacamos esta comprobación a una función? Se repite en dos sitios»
13

Merge y limpieza

Cuando el PR está aprobado, el autor lo mergea.

  1. En el PR aprobado: Merge pull request → Confirm merge.
  2. GitHub borra la rama remota automáticamente (lo configurasteis en el paso 3).
  3. En vuestro ordenador, actualizad main y borrad la rama local:
git checkout main
git pull origin main
git branch -d feature/2-clase-tablero

Los demás, en cuanto vean el merge, hacen el ciclo del paso 10 para traerse esos cambios a su rama.

¿Por qué merge commit y no squash? Así en main se ven todos los commits de cada persona con su autor. Es como podéis demostrar (y como podemos ver) quién ha hecho qué.
14

Resolver conflictos

Un conflicto aparece cuando dos personas cambian las mismas líneas. No es un error: es normal al trabajar en equipo.

# Al hacer git merge main desde vuestra rama:
CONFLICT (content): Merge conflict in variables.py

# En el archivo aparece esto:
<<<<<<< HEAD
TAMANO_TABLERO = 10
=======
TAMANO_TABLERO = 12
>>>>>>> main
  • Lo de arriba (HEAD) es lo que hay en vuestra rama. VS Code lo llama Current Change.
  • Lo de abajo (main) es lo que viene de main. VS Code lo llama Incoming Change.

Decidid qué versión vale (hablad con quien hizo el otro cambio si hace falta), dejad el archivo como debe quedar, sin las marcas <<< === >>>, y cerrad el merge:

git add variables.py
git commit --no-edit
git push origin feature/2-clase-tablero
VS Code os enseña los conflictos con los botones Accept Current Change, Accept Incoming Change y Accept Both Changes. Es más cómodo que borrar las marcas a mano. Si os liais, git merge --abort deja la rama como estaba antes del merge.

Consejos para la demo

  • Tened el terminal abierto en la carpeta del proyecto antes de empezar, con la letra grande.
  • Ejecutad python main.py una vez antes de presentar para comprobar que arranca.
  • Una partida completa es larga. Para enseñar el final en 3 minutos, preparad un tablero de demo con menos barcos: si todo está en variables.py, es cambiar una línea. Con np.random.seed() sabréis además dónde caen los barcos.
  • Quien habla no es quien teclea. Repartíos los papeles.
  • Si algo falla en directo, no os agobiéis: contad qué está pasando. Saber depurar también cuenta.
La idea de fondo: no se trata solo de que el juego funcione, sino de demostrar que sabéis lo que habéis construido y que habéis trabajado como un equipo de verdad. El proceso (issues, PRs, revisiones) importa tanto como el resultado.
